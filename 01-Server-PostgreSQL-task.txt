ЗАДАНИЕ 1. ВЫДЕЛЕНИЕ СЕРВЕРА ИГРЫ «СИМВОЛЫ» И ПЕРЕХОД НА POSTGRESQL

Выполни работу в коде, подготовь проверенный проект и инструкции запуска. Одного плана недостаточно.

1. Цель и исходная точка

Создай независимо собираемый и запускаемый проект Server в папке Server/ репозитория https://github.com/votarumshee/symbols. Здесь же впоследствии появится Android-проект Client/. Сервер должен работать с PostgreSQL вне Cloudflare/Sites и обслуживать будущий Kotlin-клиент через HTTPS и WebSocket. Сохрани правила игры, аккаунты и накопленный прогресс.

Исходники находятся в ветке export/simvoly-game, проверенный коммит 8c953993d57a887112a75c4b0a69bb2a376ea1eb. Не начинай с пустого main: на момент подготовки задания в нём только Initial commit с LICENSE. Проверь актуальное состояние репозитория и сохрани чужие изменения. Работай в ветке feature/server-postgresql, созданной от экспортированной версии либо её согласованного продолжения.

Действующая игра: https://simvoly-game.votarumshee.chatgpt.site/. Сайт, его БД и настройки публикации не изменяй в рамках разработки. LICENSE GPL-3.0 и сведения об исходных авторах сохрани.

Актуальный путь игры: dist/index.html → dist/next.mjs → /api/v2 → server/v2.mjs. dist содержит оригинальные исходники, а не только результаты сборки. Исторические RULES.md, старый app.mjs и отдельные тесты могут описывать прежнее поведение: сверяй их с этим актуальным путём.

Сейчас сервер написан на JavaScript ES modules для Cloudflare Workers. Основные файлы: server/worker.mjs, server/v2.mjs, server/arena-engine.mjs. Часть правил импортируется из dist/*.mjs. БД — Cloudflare D1, совместимая с SQLite; Drizzle-схема — db/schema.ts, исходные миграции — drizzle/. R2 AVATARS используется для чтения прежних пользовательских аватарок; новая загрузка аватарок отключена.

2. Выделение проекта Server

Базовый стек: Node.js 24 LTS, JavaScript ES modules, Fastify, node-postgres (pg), node-pg-migrate, PostgreSQL 17 с актуальным исправляющим выпуском. Зафиксируй совместимые версии и lock-файл. Сохрани существующую игровую логику на JavaScript; переписывание сервера на Kotlin в эту задачу не входит.

Учти регистр имени папки: в исходниках уже есть server/, а на обычной Windows она совпадает с Server/. Не пытайся хранить обе папки одновременно. До реорганизации сохрани запускаемый эталон базового коммита в отдельной копии/worktree. Переименование зарегистрируй в Git через временное имя (server → server-rename-tmp → Server), затем перестрой содержимое нового проекта. Проверь точный регистр путей также на Linux в CI; исходную реализацию сравнивай с сохранённым эталоном.

Последовательность:
— Составь карту актуальных функций, HTTP-маршрутов, правил, таблиц и Cloudflare-зависимостей. Зафиксируй поведение и тестовые сценарии до переноса.
— Перенеси обработку запросов из Worker в обычное HTTP-приложение. Отдели transport, services, domain, repositories, config и фоновые задания без дробления на микросервисы.
— Вынеси используемые сервером чистые правила из dist в Server/src/domain. Сервер не должен зависеть от Client/, браузерного DOM, localStorage или старой папки dist.
— Создай собственные package.json, lock-файл, конфигурацию, тесты и Dockerfile в Server/. Сборка должна выполняться из Server/ без зависимостей, установленных в корне старого проекта.
— Заменяй D1 на полноценный слой доступа к PostgreSQL. Не используй глобальную замену символов SQL и не представляй старый SQLite-адаптер как готовую PostgreSQL-реализацию.
— Замени env.DB, env.AVATARS, Cloudflare-заголовки и привязку к Sites. Ресурсы отдавай отдельными файлами с кешированием; не встраивай все PNG в серверный JavaScript/Base64. Если сохранение старых аватарок требует приватного R2-экспорта, подготовь отдельный импорт.
— Сохрани экспорт как доступный эталон до прохождения проверок. Не удаляй исходную реализацию до подтверждения функционального соответствия.

Перенеси все актуальные режимы: обычный поиск игры, дуэль, команды 2×2, испытания, комнаты по коду, два игрока на одном устройстве; обучение, оба размера поля, ботов, таймеры, результаты, опыт, звания, задания, инвентарь, улучшения, скины, рамки, аватарки, кейсы и рынок. Не включай отключённые промокоды и загрузку произвольных аватарок. Расхождения правил и необходимые исправления перечисли отдельно.

3. PostgreSQL и первая миграция на пустую БД

В database/postgresql/ уже есть экспортные SQL-файлы. Их создание схемы и наполнения проверялось на PostgreSQL 17, но сама игра пока с PostgreSQL не работает. Используй SQL как исходный материал, не как доказательство завершённого переноса.

Создай Server/migrations/ и первую версионируемую миграцию 0001_init. Она должна выполняться на пустой, заранее созданной PostgreSQL-БД и создавать всю необходимую схему: таблицы, ограничения, внешние ключи, индексы и служебные структуры. Создание самой БД и ролей опиши отдельно: обычный пользователь приложения не должен иметь CREATEDB/superuser.

Сопоставь с новой схемой все 9 исходных таблиц: profiles, matches, recovery, recovery_limits, vaults, listings, arenas, operations, account_sessions. Для переименованных, объединённых и устаревших таблиц укажи правила переноса. Добавь необходимые структуры для надёжных повторов команд, событий и фоновой обработки.

Обязательно:
— Перепиши SQLite-специфичные параметры ?, INSERT OR IGNORE, JSON-функции, генерацию идентификаторов и другие конструкции в корректный PostgreSQL SQL с параметризацией.
— Храни деньги в целых минимальных единицах; не допускай округления через float. Для существующих price/price_cents подготовь явное преобразование с проверкой.
— Сохрани идентификаторы игроков и сущностей при импорте; не предполагай, что все старые ID являются UUID. Зафиксируй формат времени UTC и безопасную передачу BIGINT/ревизий между PostgreSQL, JavaScript и Kotlin.
— Используй JSONB для сложного состояния там, где это оправдано; поля поиска, связей, сортировки и денежных инвариантов сделай проверяемыми и индексируемыми. Не нормализуй все данные только ради нормализации.
— Обеспечь журнал применённых миграций и блокировку конкурентного запуска. Повторный db:migrate должен быть безвредным; ошибочная миграция не должна оставлять частично применённую схему. Уже применённые миграции не переписывай.
— Реализуй команды npm run db:migrate, npm run db:seed и npm run db:status. В production миграции запускаются отдельным контролируемым шагом перед стартом приложения; автоматический DROP/reset при запуске запрещён.

Отдельно создай воспроизводимое начальное наполнение справочников. В экспорте database/content.json соответствует 676 справочным записям и 456 связям. game_content/game_content_links добавлены при экспорте: старая игра читает константы из JS, а не из этих таблиц. Выбери единый источник игрового контента, версионируй его и подключи к новой реализации. Клиент получает из API доступные ему параметры и описания, а сервер использует ту же версию. Исполняемые формулы и правила не подменяй справочными строками. Если структура изменилась, покажи соответствие исходному наполнению.

Повторный seed не дублирует контент и не меняет данные игроков. Тестовые аккаунты создаются отдельной dev-командой. Проверь кириллицу, связи, цены, веса выпадения, диапазоны и ограничения.

Критерий: из чистого клона и пустого PostgreSQL-тома документированными командами создаются схема и справочники, запускается Server, регистрируется синтетический игрок и завершается партия. Повторный запуск миграций/seed и перезапуск сервера сохраняют результат.

4. Сохранение аккаунтов и прогресса

Это обязательное требование владельца. Первая миграция создаёт структуру; перенос живых данных — отдельная операция.

Публичный ZIP и GitHub НЕ содержат рабочие аккаунты, сессии, коды восстановления, историю игроков и приватные изображения. Подготовь инструмент импорта из приватного экспорта D1/SQLite с режимом dry-run, отчётом сверки и защитой от повторного импорта. Проверяй его на синтетической базе старого формата. Если production-экспорт ещё не предоставлен, заверши инструмент и тесты, затем укажи точный необходимый источник; не заявляй, что реальные игроки уже перенесены.

Переноси идентификаторы, никнеймы, прогресс, баланс, инвентарь, владение косметикой, улучшения, опыт, звания, историю, предложения рынка и необходимые данные восстановления. Сверяй количество записей, суммарные балансы и владение предметами, а не только отсутствие ошибок SQL. Непереносимые строки показывай в приватном отчёте, не отбрасывай молча.

Предусмотри подтверждённый вход существующего игрока на Android через действующий механизм восстановления либо безопасный переходный обмен. Изучи формат хешей и привязку сессий; проверь совместимость. Данные localStorage телефона сами на Android не попадут. Не позволяй клиенту прислать произвольный «старый прогресс» и зачислить себе деньги или предметы. Для исключительно локальных данных опиши отдельный доверенный способ переноса и ограничения.

Подготовь пошаговый runbook переключения: резервная копия, пробный импорт, сверка, временная остановка записей в старую БД, финальный экспорт, импорт, проверка восстановления аккаунтов, переключение клиентов и план отката. Не допускай независимых записей в старую и новую БД после переноса. Политику незавершённых матчей и резервирования предметов на рынке опиши явно. Откат после появления новых записей должен учитывать эти записи, а не просто вернуть старую копию.

Реальный cutover и изменение рабочего сайта выполняются только после согласования проверенного результата с владельцем. Приватные дампы, токены и секреты не коммить и не включай в публичные артефакты.

5. Общий контракт с будущим Client

До реализации сетевого слоя Kotlin-клиента зафиксируй новую версию API /api/v3. Создай в корне contracts/openapi.yaml, contracts/events.schema.json, примеры запросов/ответов и документ совместимости. Это общий контракт двух проектов. Старое /api/v2 не переименовывай механически: документируй переход и при необходимости ограниченный адаптер.

Базовые принципы:
— HTTPS/JSON для чтения и команд; авторизованный WSS /api/v3/events для уведомлений. Все изменения игрового состояния проходят единый обработчик HTTP-команд, чтобы не поддерживать две независимые реализации действий.
— Определи bootstrap: профиль, активный матч/очередь, серверное время, версии контента и поддерживаемого API. Отдельные загрузки нужны только для отсутствующего или изменившегося содержимого.
— Предусмотри каталог с версией и ETag, снимок матча, команды матча, профиль/инвентарь, рынок с пагинацией и фильтрами, экономические операции, аккаунт/восстановление/выход/удаление, жалобы на публичные никнеймы и блокирование нежелательных взаимодействий.
— Опиши авторизацию, DTO, допустимые значения, ограничения, единицы измерения, ошибки, HTTP-статусы, лимиты и Retry-After. Не выдавай технические stack trace пользователю.
— События содержат eventId/cursor, тип, идентификатор сущности, revision и serverTime; связанные с командой — commandId. Дубликаты допустимы, повторное применение эффекта недопустимо.
— Первый вход и восстановление после разрыва получают согласованный snapshot + cursor; затем идут изменения. Пропуск истории или ревизии приводит к повторной синхронизации. Зафиксируй порядок подписки и снимка, чтобы не потерять событие между ними.
— Храни событие/outbox атомарно с изменением БД и доставляй после commit. История ограничена сроком/объёмом; просроченный cursor возвращает требование нового snapshot. Клиент не должен зависеть от обещания exactly-once доставки по сети.
— Отправляй игроку только его разрешённое представление матча и общедоступные сведения соперников. Закрытые клетки, случайные seed, чужой инвентарь, сессии и внутренние поля не должны утекать через snapshot или события.

Авторитетны только серверные правила: клиент не назначает баланс, награды, случайные выпадения, доступные предметы, победителя и время завершения хода.

6. Оптимизация запросов и самостоятельная обработка матчей

Сейчас dist/next.mjs опрашивает матч примерно каждые 900 мс, а профиль вне матча — каждые 10 секунд. При 200 активных игроках один только частый опрос составляет около 222 запросов/с. В текущем коде tick вызывается при обращениях клиента; он запускает ботов и таймеры. Нельзя просто убрать polling.

— Создай серверный планировщик для очередей, ходов ботов и истечения времени хода. Сохраняй сроки в БД, восстанавливай работу после перезапуска. Обеспечь единственного исполнителя операции через блокировки/аренду задания, включая случай двух процессов. Не держи транзакцию открытой, пока ожидается таймер.
— При исправном WebSocket постоянный polling матча/профиля отсутствует. Heartbeat служит проверке соединения и не записывает профиль в БД.
— Передавай небольшие события/изменения вместо полного профиля, каталога и поля в каждом ответе. Не отправляй неизменившиеся данные. Пакетируй связанные изменения одной операции без заметной задержки хода.
— Для среды без WebSocket предусмотри ограниченный long polling изменений по cursor, а не возврат к запросам каждые 900 мс.
— Обновляй last_seen с ограниченной частотой, например не чаще одного раза в 30–60 секунд; игровое время хода рассчитывай независимо.
— Ограничь пул PostgreSQL, устрани N+1, индексируй реальные выборки рынка, очереди и событий. Используй EXPLAIN ANALYZE на синтетических объёмах. Не добавляй Redis, Kafka или Kubernetes без измеренной необходимости.

7. Целостность, безопасность и публичный запуск

Покупка, продажа, открытие кейса, улучшение, ход и награда должны быть атомарны. Для денежных и игровых команд используй idempotency key, связанный с пользователем, типом команды и хешем параметров. Повтор после сетевой ошибки возвращает прежний результат без нового списания; тот же ключ с другими параметрами отклоняется. Установи и документируй срок хранения результатов повторов.

Блокируй необходимые строки в устойчивом порядке либо используй проверяемые ревизии с полным rollback при конфликте. Одновременная покупка одного лота должна иметь одного победителя. Повторное завершение матча не выдаёт награду второй раз. Нельзя подтвердить успех, если условное обновление не затронуло строку.

Сделай проверку принадлежности аккаунта/матча/лота, валидацию входа, лимиты размера тела, rate limit регистрации/восстановления/команд, ограничение соединений и времени запросов. Доверяй IP-заголовкам только от настроенного reverse proxy. Устрани возможность зачисления через старые sync/progress и ленивый импорт клиентского прогресса.

Реализуй управляемые сессии с хешированием токенов на сервере, сроком действия, отзывом и безопасным восстановлением. Выход и удаление аккаунта должны отзывать доступ. Для будущих магазинов нужны работающие удаление аккаунта/данных и внешний веб-путь подачи запроса; подготовь минимальную страницу и API, защищённые от удаления чужого аккаунта. Подготовь обработку жалоб на публичные никнеймы и простой административный инструмент без создания большой админ-панели.

Развёртывание: Docker Compose для Server + PostgreSQL + Caddy на одном VPS, база доступна только во внутренней сети. Подготовь .env.example без секретов, health/ready, graceful shutdown, структурированные логи без токенов/приватных данных, метрики задержек/ошибок/пула/событий и автоматические резервные копии вне сервера. Проверь восстановление резервной копии в отдельную пустую БД. Опиши DNS, HTTPS/WSS, порты, хранение данных, обновление и откат. Домен и доступы не выдумывай, инфраструктуру не покупай.

8. Проверки и критерии приёмки

Добавь значимые автоматические проверки с настоящим PostgreSQL:
— Миграции и seed с нуля, повторный запуск, сохранность после рестарта.
— Соответствие ключевых правил оригиналу: фиксированное время и контролируемая случайность, обучение, режимы, размеры поля, боты, таймеры, награды и экономика.
— Два покупателя одного лота, повтор команды после timeout, одновременные ходы, конфликт ревизий, сбой внутри транзакции, повторная доставка события и повторное завершение матча.
— Отсутствие клиента не останавливает ход бота/таймер; рестарт восстанавливает сроки; два обработчика не выполняют один шаг дважды.
— Восстановление WebSocket, cursor/snapshot без пропусков, отсутствие утечек скрытого состояния, запрет поддельного прогресса и действий от чужого аккаунта.
— Пробный импорт старой БД сохраняет аккаунты/балансы/владение; восстановление старого аккаунта работает.

Проведи воспроизводимый нагрузочный тест сначала на 50, затем на 200 активных игроках с действиями, матчами и переподключениями. Укажи реальное оборудование, объём БД, сценарий, RPS, трафик, CPU/RAM и задержки. Инженерные ориентиры для проверки на VPS 4 vCPU/8 ГБ: p95 обычных API-команд <200 мс, p95 доставки события после commit <500 мс, технические ошибки <1%. Это цели измерения, а не заранее гарантированная вместимость. Если такого стенда нет, приложи сценарий и честно укажи непроверенное.

Сравни новый обмен со старым polling на одинаковом сценарии. Отдельно посчитай HTTP-запросы, WebSocket-сообщения, байты и записи БД. В спокойном подключённом состоянии не должно быть регулярной перезагрузки профиля или heartbeat-записей в БД; целевой ориентир — минимум 90% сокращения HTTP-запросов относительно старого опроса.

9. Результат и передача следующему агенту

Передай:
— Код Server/, миграции, seed, импорт, тесты, конфигурацию и CI.
— contracts/ с примерами, версиями и точным коммитом для Client.
— README с точными командами установки/запуска; инструкцию первой миграции; runbook переноса игроков, backup/restore и развёртывания.
— Отчёт: что перенесено, что изменено, что реально проверено, известные ограничения, результаты нагрузки и перечень недостающих данных для production.

Коммить в рабочую ветку. Если GitHub-доступ настроен, отправь ветку и создай draft PR в export/simvoly-game либо актуальную согласованную интеграционную ветку; main не перезаписывай и PR не сливай автоматически. Используй настроенную авторизацию; GH_SYMBOL_TOKEN можно читать только как секрет среды, если он доступен. Значение токена не запрашивай в чате и не записывай в Git URL/логи/файлы. Если доступа нет, выдай коммит и патч/архив, не задерживая локальную работу. Сохрани автора Initial commit по ранее согласованному пожеланию владельца.

Финальный отчёт должен разделять «готово и проверено локально», «нужен staging» и «ожидает рабочего дампа/доступов/согласования переключения». Не называй сохранение живых аккаунтов завершённым до реального импорта и сверки.

Работай этапами: выделение → PostgreSQL/миграция → API/события → импорт → проверки и развёртывание. Сохраняй проверенные промежуточные результаты отдельными коммитами и кратко сообщай текущий этап и препятствия. Для передачи исходников используй обычный Git; не кодируй изображения вручную в сообщениях и не возобновляй бесконечно одну неудачную загрузку. При ограничении инструмента сохрани готовые файлы и укажи конкретный незавершённый шаг.
