ЗАДАНИЕ 2. ANDROID-КЛИЕНТ «СИМВОЛЫ» НА KOTLIN И ПЕРВАЯ ПУБЛИЧНАЯ ВЕРСИЯ

Реализуй приложение и подготовь проверенные сборки с материалами релиза. Одного плана или макетов недостаточно.

1. Цель, репозиторий и зависимость от Server

Создай независимо собираемый Android-проект Client в папке Client/ репозитория https://github.com/votarumshee/symbols. Соседний проект Server/ — перенесённый игровой сервер на PostgreSQL. Оба проекта находятся в одном репозитории. Название приложения для игроков — «Символы». Первая публичная версия готовится для Google Play И RuStore. Существующие аккаунты и прогресс должны сохраняться.

Исходная игра: https://simvoly-game.votarumshee.chatgpt.site/. Проверенная экспортированная версия находится в ветке export/simvoly-game, коммит 8c953993d57a887112a75c4b0a69bb2a376ea1eb. Актуальный браузерный путь: dist/index.html → dist/next.mjs → /api/v2 → server/v2.mjs. Исторические RULES.md и старые тесты могут не соответствовать нынешним правилам.

Перед началом сетевой интеграции получи завершённый коммит серверной задачи: Server/ и contracts/ с новым /api/v3. Создай feature/client-kotlin от этого коммита либо актуальной интеграционной ветки, которая уже содержит Server. Не начинай с main, если там всё ещё только LICENSE. Запиши базовый SHA.

Источник истины для API — contracts/openapi.yaml, contracts/events.schema.json и примеры, подготовленные серверным агентом. Если Server ещё не готов, можно делать UI и тесты на моках согласованного контракта, но нельзя объявлять интеграцию завершённой. Не проектируй независимо второй несовместимый протокол. Выявленные изменения API сначала отрази в общем контракте и согласованной серверной реализации, затем в клиенте.

2. Архитектура Kotlin-приложения

Используй нативный Kotlin, Jetpack Compose, ViewModel/StateFlow, Coroutines и однонаправленное обновление UI. Игровое поле реализуй через Compose/Canvas; перенос не должен сводиться к WebView со старой страницей. Браузерное открытие справочных ссылок допустимо.

Сетевой слой: Ktor Client с OkHttp engine для HTTPS/WSS и kotlinx.serialization. Отдели DTO, repositories, состояние экранов и UI. Настройки храни через DataStore, небольшой устойчивый кеш — в подходящем локальном хранилище; Room добавляй только при реальной необходимости. Токены должны быть зашифрованы с использованием ключа Android Keystore и исключены из резервного копирования/логов. Не сохраняй их открытым текстом в обычном DataStore.

Создай собственные Gradle Kotlin DSL, Gradle Wrapper, version catalog и CI. Зафиксируй совместимые стабильные версии Kotlin, Android Gradle Plugin, Compose и библиотек. Базовый minSdk — 26; при необходимости его изменить приведи обоснование. compileSdk/targetSdk выбирай по действующим требованиям магазинов на дату выпуска. На дату подготовки задания, 6 октября 2026 года, Google Play требует для новых обычных Android-приложений targetSdk не ниже 36; перепроверь перед отправкой.

Сделай dev/staging/prod-конфигурации с разными адресами API и раздельными тестовыми данными. В release — только HTTPS/WSS, проверка сертификата включена, cleartext запрещён. Не оставляй localhost, тестовые аккаунты, GH_SYMBOL_TOKEN, ключи PostgreSQL или административные секреты в APK/AAB. Клиент никогда не подключается к PostgreSQL напрямую.

Server остаётся единственным источником истины о победе, балансе, выпадениях, наградах, времени и владении предметами. Kotlin может рассчитывать отображение, подсказки и анимации, но не назначать результат операции. Не создавай независимую копию таблиц цен/баланса: используй версионируемый контент сервера и проверенную совместимость локальных ресурсов с его ID.

3. Функциональный перенос

Сначала составь матрицу «экран/сценарий исходной версии → экран Client → проверка». Сверь код и локально запущенную экспортированную игру; не считай одни устаревшие документы достаточным эталоном.

Перенеси:
— Первый запуск, выбор никнейма, создание аккаунта, профиль, восстановление, выход и существующие сценарии работы с несколькими аккаунтами.
— Обучение, актуальные правила и справочник символов.
— Обычный поиск соперника, дуэль, команды 2×2, испытания, комнаты по коду, два игрока на одном устройстве; ожидание, отмену поиска, вход/выход из матча.
— Оба размера поля 10×14 и 28×20, размещение и выбор фигур, доступные действия, очередность, ограничение времени, ботов, боевые эффекты, завершение партии и результаты.
— Опыт, уровни, звания, задания и историю матчей.
— Инвентарь, улучшения, скины, рамки, аватарки, магазин за игровые рубины, кейсы, рынок: фильтры, предложения, покупку, продажу, отмену и отображение точной цены.

Сохрани актуальную механику и баланс. Не включай отключённые промокоды, загрузку пользовательских изображений, оплату реальными деньгами, рекламу или социальный чат. Сейчас покупки идут за игровую валюту; платёжного шлюза нет. Добавление монетизации требует отдельного задания, а не автоматического подключения магазинных SDK.

Существующие графические ресурсы и обозначения адаптируй к Android с сохранением прав и сведений об авторах. Не заменяй правила или важные элементы только потому, что их сложнее перенести. Предусмотри отсутствие устаревшей пользовательской аватарки: это не должно мешать входу и игре.

На узком экране большое поле должно оставаться управляемым: масштаб/панорамирование или другой проверенный способ выбора клетки без случайных действий. Не уменьши размер игрового поля ради вёрстки. Сделай состояния загрузки, пустых списков, недостаточного баланса, отклонённого хода, потери сети, устаревшей версии и недоступности сервера. Показывай понятный результат операции, не вечный спиннер.

4. Восстановление прежних аккаунтов

Приватные данные игроков не входят в публичный архив. Их импортирует Server отдельным инструментом; браузерный localStorage автоматически в Android не переносится.

Реализуй работающий пользовательский путь входа в существующий аккаунт через согласованный сервером механизм восстановления/переноса. Добавь понятную инструкцию, как получить необходимые данные в старой игре до переключения. Не проси пользователя передавать токены в чат поддержки и не отправляй их в аналитику. Не создавай новый пустой аккаунт молча при ошибке восстановления.

Проверь на синтетическом аккаунте, созданном в старой реализации и импортированном в PostgreSQL: сохранены идентификатор, ник, баланс, инвентарь, улучшения, косметика, звание и история. Вход на другом устройстве и перезапуск приложения не должны терять прогресс или повторно выдавать стартовые награды.

Если рабочего импорта/сервера ещё нет, укажи зависимость явно. Не маскируй её локальным профилем с выдуманным балансом. После удаления или смены аккаунта очищай приватный кеш и старые подписки; ответы предыдущей сессии не должны попасть в новый профиль.

5. Оптимизация клиент-серверного обмена

Исходный клиент опрашивает матч примерно каждые 900 мс и профиль каждые 10 секунд. В Client такой цикл переносить нельзя. Server должен самостоятельно двигать ботов и таймеры и предоставлять события по /api/v3/events. Все игровые изменения отправляй HTTP-командами, а уведомления получай через WebSocket.

Реализуй:
— Один сетевой клиент и не более одного активного WebSocket на сессию приложения, а не по соединению на каждый экран. Авторизация в защищённом заголовке, без токена в URL.
— На входе bootstrap для профиля, активной партии и версий данных. Загружай каталог/ресурсы только при отсутствии кеша или изменении версии; используй ETag/If-None-Match и Cache-Control по контракту.
— При исправном WebSocket не выполняй периодические запросы профиля и матча. Отрисовка таймера, анимации и Compose recomposition не должны генерировать HTTP-запросы.
— Применяй события по eventId/cursor и revision; отбрасывай дубликаты, не откатывай состояние запоздавшим ответом. При пропуске ревизии или недоступном cursor получай новый снимок и возобновляй поток по протоколу Server.
— Снимок профиля/поля загружай при входе, необходимой сверке или восстановлении; после обычного хода применяй ответ команды и события без повторной загрузки всего профиля и каталога. Эффект ответа и того же события применяется один раз.
— Переподключение с ограниченным exponential backoff и jitter; учитывай состояние сети и Retry-After, исключи цикл бесконечных быстрых повторов. При отказе WebSocket используй только предусмотренный контрактом ограниченный long polling.
— При уходе приложения в фон прекращай необязательные запросы и закрывай соединение после короткого согласованного переходного периода. Не запускай постоянный foreground service ради polling. При возврате восстанавливай состояние с сервера. Ход и таймер на сервере при этом продолжаются; интерфейс должен объяснять последствия выхода из партии.
— Heartbeat выполняется с согласованной частотой, например раз в 25–30 секунд, только для живости соединения. Не отправляй запись профиля как heartbeat.
— Для рынка используй серверную пагинацию, ограниченные выборки, отмену устаревших запросов и debounce поиска/фильтра около 300 мс. Не скачивай весь рынок и не делай отдельный запрос на каждую строку.
— Дедуплицируй параллельные загрузки одинаковых данных. Отменяй запросы, потерявшие смысл после навигации; кеш различай по аккаунту. Ограничь размеры и срок кеша, очищай его при выходе/удалении аккаунта.
— Для изображений используй подходящие размеры и кеширование; не передавай PNG в JSON/Base64 при каждом запросе. Статические изображения можно включить в приложение, оставив обновляемый каталог версионируемым.

Денежные и игровые команды передавай с устойчивым idempotency key/commandId и ожидаемой ревизией. После timeout выясни результат прежней команды либо повтори её с тем же ключом: отмена клиентского запроса не означает отмену серверной операции. Не повторяй покупку с новым ключом автоматически. Двойное нажатие не должно приводить к двойному списанию.

Для важных незавершённых операций сохраняй минимум данных, необходимых для сверки после перезапуска. Просроченные ходы не отправляй заново. В офлайне разрешено отображать явно обозначенный кеш; не выдавай подтверждённые награды и не накапливай произвольные покупки/ходы для поздней отправки.

Измерь на одинаковом сценарии старую и новую версии: HTTP-запросы, WebSocket-сообщения, исходящие/входящие байты за 10 минут, переподключения и задержку отображения хода. Отдельно покажи спокойное состояние и активный матч. Цель для спокойного состояния — отсутствие регулярных загрузок профиля/поля и минимум 90% сокращения HTTP-запросов относительно старого polling. Число открытых соединений и heartbeat учитывай отдельно, чтобы сравнение не было формальным.

6. Готовность к публичной версии

Качество Android:
— Проверь Back-навигацию, системные отступы/edge-to-edge, поворот и пересоздание Activity, возврат из фона, уничтожение процесса и восстановление активной партии.
— Сделай читаемые русские тексты, масштабирование шрифта, достаточные области нажатия, понятные обозначения состояния помимо цвета, подписи для TalkBack и возможность уменьшить интенсивные эффекты. Бесконечные анимации в фоне останови.
— Проверь производительность на устройстве среднего/начального уровня: не выполняй сеть, JSON и тяжёлые вычисления на главном потоке; минимизируй лишние перерисовки поля, измерь запуск, память и длительность кадров. Цель — плавная игра без ANR, зависаний и накопления памяти.
— Работай без обязательной зависимости от Google Play Services, чтобы RuStore-сборка работала на устройствах без них. Для первого выпуска достаточно общей кодовой базы и одинакового функционала; отдельные store-flavors нужны только при реальном отличии интеграций.

Аккаунты и данные:
— Добавь в приложение удаление аккаунта с подтверждением и работающим серверным результатом, ссылку на внешний путь удаления/запроса удаления, политику конфиденциальности и контакт поддержки.
— Реализуй отправку жалоб на публичные никнеймы и блокирование нежелательных взаимодействий согласно серверному контракту и применимым требованиям магазинов. Не ограничивайся декоративной кнопкой, сообщение должно попадать в доступный обработчику канал.
— Собери перечень реально обрабатываемых данных, сетевых адресов и сторонних SDK. Подготовь тексты для Google Play Data safety и соответствующих деклараций RuStore по фактическому поведению. Не добавляй рекламные/аналитические SDK без отдельного решения владельца.
— Уточни у владельца целевую возрастную аудиторию и страны распространения до окончательного заполнения магазинных анкет. Не считай приложение детским только потому, что его создал ребёнок, и не заявляй автоматически 18+. Проверь применимые требования к выбранной аудитории, кейсам и публичному контенту. Условия/вероятности получения предметов должны быть понятны игроку.
— Сохрани LICENSE и сведения о сторонних компонентах; подготовь сведения об исходниках, соответствующих выпускаемой версии. Проверь права на графику, название и используемые материалы до отправки.

7. Сборки и подготовка Google Play / RuStore

Предварительные параметры: rootProject.name = Client, название «Символы», versionName = 1.0.0 и versionCode = 1, если более ранних магазинных выпусков нет. Предложение для applicationId — com.votarumshee.symbols; перед первым магазинным выпуском владелец должен подтвердить окончательное имя пакета. Не регистрируй его от имени владельца без согласования.

Подготовь release AAB для Google Play и подписанный release APK для RuStore, а также APK для внутренней проверки. RuStore принимает и AAB, но APK достаточно для первоначального плана. Оба магазина должны использовать согласованную схему подписи и версий: один applicationId и совместимый сертификат подписи установленных приложений, чтобы обновление между источниками не требовало удаления аккаунта/приложения.

До включения Play App Signing продумай использование ключа подписи приложения, контролируемого владельцем и пригодного для обоих магазинов. Различай app signing key и upload key: подпись загружаемого AAB не доказывает совпадение подписи установленного APK. Не выбирай необратимую схему только ради быстрого выпуска. Подготовь инструкцию настройки и проверки SHA-256 сертификатов. Ключи, пароли и их резервные копии не коммить и не помещай в публичные артефакты.

Если окончательные ключи и данные ещё не предоставлены, заверши код, тестовые сборки и подготовку релизной конфигурации; затем запроси конкретные параметры. Отладочную или неподписанную сборку не называй готовой к публикации. Проверь release-вариант с включёнными R8/оптимизацией, сохранение сериализации/ресурсов, отсутствие debug-функций и корректность работы после установки/обновления. Проверь поддержку 16-КБ страниц памяти, если зависимости содержат нативные библиотеки.

Подготовь отдельно для каждого магазина: краткое и полное описание, иконку, реальные скриншоты работающего Android-приложения в требуемых размерах, категорию, проект ответов по возрасту/контенту и данным, release notes, контакты/URL поддержки, privacy policy и удаления аккаунта, сценарий доступа для модератора. Недостающие контактные данные и URL пометь как требующие владельца; не выдумывай их и не отправляй анкеты с заглушками.

Google Play: перепроверь targetSdk и текущие требования аккаунта. Для личных аккаунтов разработчика, созданных после 13.11.2023, на дату подготовки задания предусмотрен закрытый тест минимум с 12 участниками, непрерывно подключёнными 14 дней, перед запросом доступа к production. Уточни применимость к аккаунту владельца и подготовь план такого теста. Эти дни и проверку магазина нельзя заменить автоматическим тестом или объявить пройденными заранее.

RuStore: проверь подпись, имя пакета, versionCode, требования к карточке/разрешениям и возможность полноценной игры без сервисов Google. Подготовь отдельную памятку загрузки и модерации. Реальную публикацию и отправку на модерацию выполняй только после согласования владельцем конкретных сборок и заполненных материалов.

8. Тестирование и критерии приёмки

Тесты должны проверять поведение, а не просто повторять структуру реализации:
— Unit-тесты преобразований DTO, состояния экранов, ревизий/дедупликации событий, денег без float, восстановления и повторов команд.
— Контрактные проверки запросов/ответов на fixtures из contracts/ и настоящем Server + PostgreSQL. Моки полезны для ошибок/задержек, но не заменяют интеграцию.
— Инструментальные UI-проверки первого запуска, восстановления аккаунта, начала/завершения партии, покупки, инвентаря и удаления аккаунта.
— Совместная игра минимум двух экземпляров Android-клиента, затем 2×2, комната по коду и матч с ботом. Проверь оба размера поля и локальный режим двух игроков.
— Потеря сети до отправки команды и после её выполнения сервером, Wi-Fi ↔ мобильная сеть, большой RTT, повторные события, 401/429/5xx, истечение сессии, фон, перезапуск процесса, рестарт Server и возвращение в активный матч.
— Одновременная покупка одного лота двумя игроками; двойное нажатие и повтор после timeout не создают второй расход/предмет. Удалённый/заблокированный аккаунт теряет доступ.
— Импортированный старый аккаунт сохраняет прогресс после входа и перезапуска; logout/account switch не показывают чужой кеш.
— На минимально поддерживаемом и актуальном Android проверь release-сборку, в том числе на устройстве/эмуляторе без Google Play Services; отдельно укажи проведённую проверку реального устройства.

Все актуальные игровые сценарии матрицы должны работать либо иметь явно согласованное исключение. В CI должны проходить сборка, lint, unit-тесты и доступные инструментальные/контрактные проверки. Приложи результаты сетевых измерений и профилирования. Не заявляй тест на устройстве или магазине, если был только эмулятор или мок.

9. Что передать владельцу

— Код Client/, Gradle Wrapper, конфигурацию и CI; обновлённые согласованные contracts/, если потребовались изменения.
— README с точными командами сборки и подключения к локальному/staging/prod Server, требованиями JDK/SDK и схемой безопасной передачи ключей подписи.
— Установочный тестовый APK, фактически подготовленные release-артефакты, SHA-256 файлов и сведения о версии/подписи; без секретов.
— Матрицу перенесённых функций, отчёт тестов, сравнение трафика, известные ограничения и инструкции проверки владельцем.
— Два комплекта материалов магазинов и общий release-checklist: staging, подтверждение переноса аккаунтов, тестирование, подпись, карточки, модерация, выпуск и контроль ошибок после выпуска.

Коммить в feature/client-kotlin. При настроенном GitHub-доступе отправь ветку и создай draft PR в интеграционную ветку, содержащую Server; main не перезаписывай и PR не сливай автоматически. Используй существующую авторизацию; секрет GH_SYMBOL_TOKEN, если доступен, не показывай и не включай в файлы/логи. При отсутствии доступа передай локальный коммит и патч/архив. Сохрани автора Initial commit согласно пожеланию владельца.

Считай разработку завершённой после проверки реального взаимодействия Client ↔ Server ↔ PostgreSQL и подготовки артефактов. В финальном отчёте отдельно обозначь внешние шаги: production-импорт игроков, домен/сервер, ключи и аккаунты магазинов, обязательный закрытый тест, модерацию и разрешение владельца на публикацию. «Подготовлено к выпуску» не означает «уже опубликовано».

Работай этапами: каркас и контракт → аккаунты → основные экраны и матч → экономика → оптимизация и проверки → материалы релиза. Сохраняй проверенные промежуточные результаты отдельными коммитами, кратко сообщай текущий этап и препятствия. Передавай файлы обычным Git или архивом без ручного Base64 в сообщениях; не теряй готовую работу из-за сбоя одного инструмента публикации.
