ЗАДАНИЕ 3. ПОДГОТОВКА PRODUCTION VDS: UBUNTU, SSH И DOCKER

Это задание для выполнения агентом, а не запрос ещё одного плана. Выполни установку, подготовь воспроизводимые файлы и проверь результат. Работай последовательно; следующее задание — 04-VDS-runtime-setup-task.txt.

1. Контекст и границы

Проект: C:\repos\EVS\symbols, origin https://github.com/votarumshee/symbols.git.
VDS: 135.106.172.96, SSH TCP/22, hostname evs-symbols.
Проверенный исходный доступ: root и локальный ключ C:\Users\vologodskiy.av\.ssh\id_ed25519_vds_symbols через SSH-агент. Не читай и не выводи закрытый ключ. Не используй прежний id_ed25519 и переменную VDS_SYMBOLS_PHRASE: они не нужны для проверенного подключения.
На 07.10.2026: Ubuntu 24.04.4 LTS x86_64, 2 vCPU, около 4 ГБ RAM, диск 50 ГБ, swap отсутствует. Docker/PostgreSQL/Caddy не установлены, UFW отсутствует, из прикладных внешних TCP-портов обнаружен только SSH. Это результаты прежнего осмотра: перепроверь состояние и правила firewall, включая ограничения провайдера, если они доступны.

VDS предназначен для production. Начинаем с новой базой и новыми аккаунтами. Не переносить D1/SQLite/R2, не трогать старый сайт, не выполнять старые задания 01/02 заново. Их требования о переносе старых игроков отменены.
В этом задании устанавливается ОС-окружение, но не запускается публичное приложение. Домен пока не предоставлен. Не покупать услуги и не менять DNS. Не запускать других агентов.

2. Проверка перед изменениями

Прочитай применимые AGENTS.md, git status, Server/README.md, Server/compose.yaml и Server/docs/deployment.md. Сохрани чужие изменения. Для новых изменений используй отдельную ветку codex/vds-production-setup, если подходящая ветка ещё не выделена; не сбрасывай текущую работу.
Проверь SSH host key по уже известной записи; изменившийся ключ не принимать автоматически. При несовпадении останови только удалённые действия и сообщи об этом.
Сними обезличенный инвентарный отчёт: ОС, RAM/CPU/диск, службы, порты, маршруты, firewall, обновления, состояние синхронизации времени. Сохрани резервные копии изменяемых конфигураций на VDS с ограниченным доступом; в Git — только несекретные шаблоны и отчёт.
Если обнаружено уже работающее приложение или данные, не считать сервер пустым и не удалять их.

3. Установка базового ПО

Установи через подписанные репозитории Ubuntu необходимые утилиты: ca-certificates, curl, gnupg, jq, rsync, sudo, ufw, unattended-upgrades, logrotate; используй уже установленные пакеты там, где это возможно.
Примени обычные обновления безопасности Ubuntu 24.04 без обновления дистрибутива на другую major-версию. Не запускай автоматически reboot; при необходимости укажи его в отчёте и подготовь процедуру проверки после перезагрузки. Не включай автоматический reboot production-хоста.
Сохрани рабочую службу синхронизации времени. UTC на сервере подходит; менять timezone не требуется.
Настрой лимиты journald и журналов Docker, чтобы журналы не заняли диск. Для 4 ГБ RAM допустим swap-файл около 2 ГБ после проверки файловой системы, свободного места и существующего swap; повторный запуск не должен создавать его заново. Swap не считать заменой достаточной RAM.

4. SSH и пользователи

Создай администратора symbols-admin с доступом по существующему открытому ключу владельца и рабочим sudo. Схему sudo документируй; не придумывай пароль, который потом потребуется извлекать из логов.
Сначала проверь вход новым пользователем и sudo в отдельном SSH-подключении. Сохрани исходную сессию во время изменений SSH/firewall. Перед reload проверь sshd -t и эффективные настройки, включая drop-in файлы и socket activation Ubuntu.
Отключи парольную SSH-аутентификацию после проверки входа по ключу. Root-вход по ключу пока сохрани как резервный; его отключение оставь отдельным завершающим действием после подтверждения рабочего административного доступа.
Создай symbols-deploy с заблокированным паролем для будущего CI/CD. Не добавляй его в docker и не выдавай безусловный sudo: управление Docker фактически даёт root-доступ. Не копируй личный ключ владельца в CI и не выдавай ему права deploy-ключа. Ограниченный механизм запуска deploy будет реализован отдельно.

5. Firewall и Docker

До включения firewall явно разреши текущий SSH TCP/22. Подготовь 80/TCP, 443/TCP и при использовании HTTP/3 — 443/UDP. Учти IPv4 и IPv6, не меняй SSH-порт. Не ограничивай SSH случайно определённым динамическим IP без рабочего запасного пути.
Установи Docker Engine из официального apt-репозитория Docker: docker-ce, docker-ce-cli, containerd.io, docker-buildx-plugin, docker-compose-plugin. Используй stable-версии и зафиксируй фактически установленные версии в отчёте. Не используй curl | sh.
Проверь совместимость firewall с выбранным сетевым backend Docker. Публикация контейнерного порта может обходить UFW; одной проверки ufw status недостаточно. Не отключай управление сетью Docker вслепую и не стирай существующий ruleset.
Включи Docker при загрузке, проверь docker version, docker compose version и запуск одноразового тестового контейнера. Удали только созданный тестовый контейнер, не выполняй общий prune.
Не устанавливай PostgreSQL, Node.js, npm, Java, Android SDK, Nginx или Caddy непосредственно в Ubuntu: runtime проекта и Caddy будут контейнерными. Не устанавливай GitHub runner на production VDS.

6. Каталоги и воспроизводимость

Подготовь согласованную структуру:
— /opt/symbols/releases: проверенные файлы релизов;
— /opt/symbols/current: ссылка на текущий релиз, создаётся при его установке;
— /etc/symbols: конфигурация и секреты, root-only по умолчанию;
— /var/lib/symbols: данные вне контейнерного слоя, включая каталог avatars;
— /var/backups/symbols: ограниченные локальные копии;
— PostgreSQL и Caddy — отдельные постоянные Docker volumes на следующем этапе.
Не делай конфигурации, читаемые privileged-сценариями, доступными на запись пользователю symbols-deploy.
Добавь в Server/deploy воспроизводимые provisioning-скрипты или конфигурацию и инструкцию повторного применения. Повторное применение не должно менять ключи, пароли, данные или дублировать правила. Учитывай LF в shell-файлах, копируемых с Windows.

7. Приёмка и отчёт

Проверь новый SSH-доступ и sudo, корректность sshd, firewall для обеих IP-семейств, автозапуск Docker, тестовый контейнер, ротацию логов, время, ресурсы и права каталогов. Из доступной внешней среды проверь SSH и отсутствие доступа к TCP/5432, 3000, 2375 и 2376. Не выдавай локальную проверку за внешнюю; если внешняя проверка недоступна, укажи ограничение.
Сохрани Server/docs/vds-system-verification.md: дата, версии, выполненные изменения, команды без секретов, результаты и что ещё требуется. Отдельно укажи необходимость reboot и способ административного входа после изменений. Не заявляй, что production-приложение уже развёрнуто.
