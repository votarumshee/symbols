ЗАДАНИЕ 4. УСТАНОВКА POSTGRESQL И КОНТЕЙНЕРНОГО ОКРУЖЕНИЯ «СИМВОЛЫ»

Выполнять после 03-VDS-system-setup-task.txt. Реализуй конфигурацию и проверь её на VDS; не ограничивайся планом. Не запускай других агентов.

1. Контекст

Репозиторий C:\repos\EVS\symbols; VDS 135.106.172.96, evs-symbols. Используй административный доступ и структуру каталогов, подтверждённые предыдущим заданием. Сохрани чужие изменения и уже работающие данные. Работай в подготовленной ветке инфраструктуры.
Начинаем с чистого листа: только схема и игровые справочники. Импорт старых игроков, D1, SQLite, R2 и работа со старым сайтом исключены. Повторное выполнение НЕ означает очистку существующей БД.
Актуальны Server/, Client/ и contracts/. Корневой README в основном описывает историческую версию. Старый dist — не клиент API v3. Android собирается отдельно и на VDS не устанавливается.
Исходный стек в репозитории: PostgreSQL 17.11-bookworm, Node 24.19.0-bookworm-slim, Caddy 2.11.2-alpine. Это зафиксированная исходная конфигурация, а не утверждение о последних безопасных версиях. Перед установкой проверь доступность и security-релизы; совместимые patch-обновления проводи с проверками, major-версии не меняй в рамках задания. Зафиксируй выбранные версии и digest.

2. Production Compose

Прочитай Server/compose.yaml, Dockerfile, .dockerignore, deploy/init-roles.sh, deploy/Caddyfile, scripts/migrate.mjs, seed.mjs, grants.mjs и docs/deployment.md.
Подготовь отдельную production-конфигурацию на их основе. Сохрани существующий локальный запуск. Используй постоянное имя Compose project symbols, чтобы смена каталога релиза не создавала новую пустую БД; имена production volumes также должны быть стабильны.
Секреты держи в /etc/symbols с ограниченными правами; не включай их в Git, образы, artifacts, команды или отчёты. Не выводи docker compose config с подставленными секретами: для проверки достаточно config --quiet. Генерируй разные стойкие URL-safe пароли PostgreSQL administrator/owner/app и METRICS_TOKEN. Повторный запуск не должен заменять существующие секреты.
Используй защищённый env-файл или совместимые secrets-файлы. Проверь, что выбранный способ реально поддерживается entrypoint/приложением: наличие *_FILE нельзя предполагать. Настрой однозначный запуск Compose с нужным env-файлом и путями независимо от текущего каталога.
В production у server и migrate должен быть один проверенный образ. Собери его из Server вне production VDS и передай как проверенный архив docker save/load либо загрузи из уже настроенного registry. Зафиксируй git commit и image ID/digest; не используй mutable latest. На этом этапе не нужно создавать полный GitHub CD или публиковать пакет без соответствующей задачи.
Для миграционного контейнера не наследуй runtime HEALTHCHECK приложения: это одноразовая задача без HTTP-сервера.
БД доступна только по внутренней Docker-сети; не публикуй 5432. Приложение — через Caddy или временно через loopback для закрытой проверки, без публикации 3000 на внешние адреса. /metrics не публиковать через Caddy.
Согласуй subnet и точный TRUST_PROXY; проверь отсутствие конфликтов маршрутов. Настрой restart policy, log rotation, разумные лимиты RAM/CPU и запас памяти ОС для хоста 2 vCPU/4 ГБ. PG_POOL_MAX=10 — исходная настройка, а не повод увеличивать max_connections без измерений.

3. PostgreSQL и чистая БД

Запусти только PostgreSQL, дождись healthcheck и проверь постоянный volume.
Создай БД symbols и роли согласно init-roles.sh. symbols_owner — владелец схемы для миграций, symbols_app — runtime с необходимыми DML-правами и чтением справочников, без superuser/createdb/createrole/DDL. Для новых миграций проверь также необходимые права на sequences и новые объекты, если они появятся.
Entry-point init-скрипты PostgreSQL выполняются только на пустом volume. При существующем volume анализируй текущее состояние; не удаляй его и не меняй пароли одной лишь правкой env.
Одноразовым migrate-контейнером выполни миграции, seed и grants. Проверь журнал миграций, 676 справочных записей и 456 связей по текущему каталогу. Не выполняй db:import, dev:seed, DROP/reset или docker compose down -v.
Проверь повторный запуск миграций/seed и отсутствие изменений в пользовательских данных. Production profiles должен оставаться пустым до настоящей регистрации пользователей.

4. Приложение и Caddy

Подготовь /var/lib/symbols/avatars с правами, необходимыми UID приложения для удаления аватаров; не выдавай ему запись во весь релиз. Проверь фактические пути монтирования и healthcheck. Запусти приложение для закрытой проверки /health и /ready.
Домен и ACME email пока не предоставлены. Если их нет, заверши установку БД и закрытую проверку приложения, подготовь Caddy и сообщи, какие значения нужны. Не подставляй выдуманный домен, не публикуй API по открытому HTTP и не ослабляй TLS Android-клиента. Это не должно блокировать независимые работы, включая резервирование.
Если владелец предоставил домен/email, проверь A и при наличии AAAA, доступность ACME, конфигурацию Caddy и постоянные тома сертификатов. Включение публичного API выполняй после успешной приёмки внешнего резервирования из задания 5. До этого Caddy можно проверять с maintenance-ответом, не открывая игровые маршруты.
После выполнения условий проверь HTTPS, WSS, недоступность /metrics извне и отсутствие прямого доступа к БД. Не считать один HTTP 200 доказательством готовности миграций, игрового API и восстановления соединений.

5. Проверки без загрязнения production

Для регистрации, игры, конкурентных команд, WSS и проверки восстановления создай отдельную временную БД с явным test-именем и отдельный проверочный экземпляр приложения. Не запускай исторические или интеграционные тесты на symbols. Внутренние тесты требуют административной тестовой роли и могут создавать/удалять тестовые БД; не выдавай эти права symbols_app.
Проверь /ready на production без создания аккаунтов. На тестовом экземпляре проверь регистрацию, bootstrap, матч, переподключение WSS, отсутствие повторного начисления при повторной команде и восстановление связи после перезапуска тестовой БД.
Проверь штатное завершение приложения и сохранность volumes. Healthcheck unhealthy сам по себе не гарантирует автоматический restart Docker: обеспечь наблюдаемость и опиши процедуру восстановления.
Очисти только собственные тестовые ресурсы по точным именам. Не делай общий volume prune. Нагрузочные измерения не считать пройденными, если выполнен только smoke-test.

6. Результат

Сохрани production Compose, несекретный env-example и команды обслуживания в Server/deploy; обнови Server/docs/deployment.md. Добавь Server/docs/vds-runtime-verification.md с git SHA, версиями/образами, структурой каталогов, результатами проверки ролей, миграций, сетей, volumes и приложения, без секретов.
Оставь возможность будущему deploy-сценарию подставлять проверенный образ для server/migrate и откатывать приложение без удаления БД. Зафиксируй, что откат образа допустим только при совместимости со схемой и контентом. Полную реализацию CI/CD и выпуск Android оставь отдельным заданиям.
В финале явно раздели: установленное ПО; закрытая проверка; готовность HTTPS; внешнее резервирование; открытие production для пользователей. Не объявляй заблокированные этапы выполненными.
