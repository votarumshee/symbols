ЗАДАНИЕ 7. ПРИВЕСТИ ANDROID UI И УПРАВЛЕНИЕ К WEB-ЭТАЛОНУ

Реализуй изменения, собери APK и проверь результат. Пользователь посмотрел текущую Android-игру и подтвердил существенное расхождение именно внешнего вида и управления с web. Техническая работоспособность API уже принята; это задание исправляет пользовательский интерфейс. Не ограничивайся планом, косметической заменой цветов или отчётом о сборке. Не запускай других агентов.

1. Контекст, эталон и границы

Проект C:\repos\EVS\symbols, Client/ — Kotlin/Compose/Canvas, Server/ — работающий API v3. Проверь применимые AGENTS.md, git status/branch, сохрани все существующие изменения и артефакты. Не делай commit/push. Не меняй серверную механику, баланс, контракты, способ авторизации, шифрование токенов или сетевую архитектуру ради UI. WebView вместо нативного клиента не допускается.

Эталон: экспорт web-игры на коммите8c953993d57a887112a75c4b0a69bb2a376ea1eb, ветка export/simvoly-game, локальная .reference/; путь dist/index.html → dist/next.mjs → /api/v2. Проверь SHA и соответствие файлов; доступный корневой dist можно использовать после сверки с этим эталоном. Главные материалы: next.mjs, next.css, style.css, icons/skins/frames/effects/rank-art и связанные ресурсы. Старые RULES.md и начальный app.mjs не заменяют актуальный next.mjs. Прочитай Client/docs/feature-matrix.md, verification.md, dependency-manifest.json, исходное задание02 и актуальное задание06/отчёт public API.

Production уже открыт на https://symbols-api.votarumshee.com. В этой задаче НЕ переключай его на тестовый upstream/maintenance, не запускай тестовых игроков или миграции на production и не меняй VDS. Пользователь мог уже создать настоящий аккаунт. Используй локальные изолированные web и Server v3 с синтетическими данными, разными БД и отдельными Android QA packages. Старые scripts public-api-stage.sh и prodQa UI через временный production route для этой задачи не подходят. Прежние backups/Caddy/таймеры не трогай.

2. Сначала зафиксируй визуальный эталон

Запусти локально экспортированную web-игру с отдельной синтетической БД. Разбери существующие локальные scripts/инструменты из предыдущих проверок, не подменяй все ответы нарисованными моками. Сними реальные эталонные экраны при мобильном viewport, сопоставимом с Android dp-размером, и при узком экране. Запиши viewport, плотность/размер Android, commit эталона и состояние синтетического аккаунта. Не сравнивай desktop web с телефоном и не обещай pixel parity по разным сценам.

Обязательные сцены: главный экран; выбор режима/размера; ожидание; поле10×14 с расстановкой королей и обычным ходом; выбор символа; направление3×3; поле28×20/масштаб; результат; инвентарь и карточка предмета; улучшения; магазин/кейс; рынок; профиль/задания/правила. Для косметики используй синтетический набор владения в тестовой БД. Сохрани реальные скриншоты до изменений и web-эталона в игнорируемом Client/artifacts/ui-parity/.

Составь короткий Client/docs/web-ui-parity.md: web-элемент/действие → текущая проблема → целевое поведение → способ проверки. Это рабочая матрица, которую нужно закрывать реализацией и свидетельствами. Сразу сообщи основному агенту пути первых web/Android сравнений и выявленные крупные расхождения, чтобы review начался до конца переделки.

3. Игровой экран и управление — первый приоритет

Восстанови исходную иерархию: компактная верхняя игровая панель, статус хода/таймер, соперник над полем и игрок под ним, само поле как основной элемент, доступная нижняя панель символов. Не оставляй игру длинной страницей с крупными стандартными заголовками, отдельными формами и подтверждением под прокруткой. Сохрани видимые нужные статусы сети/ошибок, но не занимай ими постоянно значительную часть игрового экрана.

Сценарии должны повторять next.mjs/chooseCell:
- В расстановке нажатие допустимой клетки крайнего ряда ставит короля без дополнительной общей кнопки подтверждения.
- В обычном ходе сначала выбирается символ из нижней панели, затем клетка. Для направленного символа открывается знакомая сетка направлений3×3 со стрелками; нажатие стрелки отправляет ход. Для ненаправленного символа допустимое нажатие клетки отправляет ход сразу.
- Телепорт: исходная фигура → целевая клетка → направление, когда оно требуется. Отмена выбора и недопустимые клетки должны вести себя как в web.
- Не показывай выпадающие списки «Символ»/«Направление», общий «Подтвердить:…», постоянные поля «Ряд/Столбец» и большой Slider как основной игровой интерфейс. Доступность сохранить: альтернативный выбор координат/semantic actions можно вынести в отдельный доступный режим; нельзя удалить TalkBack-путь ради внешнего вида.
- Сохрани очередность, busy/disabled, запрет чужого хода, корректность ориентации обеих сторон и локальной игры, реальные остатки символов и серверные отклонения. Один завершённый жест = максимум одна команда; drag/pinch не отправляют ход.

Поле10×14 первоначально должно быть обозримым на обычном телефоне; размеры игры не менять. Для28×20 обеспечь удобное увеличение и перемещение, согласованные с web: компактная кнопка масштаба и/или естественные жесты, без постоянной громоздкой панели. Проверь выбор крайних клеток, обрезание, область нижней панели, system insets, маленький экран и увеличенный шрифт. На увеличенном поле перемещение не должно случайно ставить фигуру.

Восстанови исходные цвета/рамки клеток, символы, состояния выбранной/недоступной фигуры, здоровье/аватары, типографическую иерархию, подсказки обучения, результаты и основные боевые эффекты. Используй исходные SVG/PNG и уже перенесённые assets. Не заменяй доступную графику emoji/буквой, упрощённой точкой или универсальной карточкой. Сравни направление/вращение/отражение фигур и эффекты на одинаковых сценах. Сервер остаётся источником результата; адаптация анимации не должна повторно применять игровое событие.

4. Остальные экраны

Главное меню вернуть к композиции web: игровая графика/название, основные действия «Играть», «Профиль», «Инвентарь», заметные улучшения и компактная вторичная навигация. Убери созданную при переносе структуру длинного списка крупных Material-карточек, если ей нет соответствия в эталоне.

Перенеси расположение и визуальную структуру выбора режимов, инвентаря/предметов, улучшений, магазина/кейсов, рынка/фильтров, профиля/званий/истории, заданий и правил. Учитывай мобильную web-компоновку и исходные модальные панели. Не превращай все эти экраны в одинаковую универсальную форму. Нативные компоненты допустимы при сохранении композиции, размеров, узнаваемой графики и последовательности действий.

Не возвращай отключённые промокоды, arbitrary avatar uploads, скрытую instant-победу, платежи или импорт старых пользователей. Сохрани необходимые Android-функции восстановления, аккаунтов, удаления, сетевых ошибок и доступности; располагай их согласованно с исходным интерфейсом. Старые инструкции об обязательном импорте отменены пользователем: начинаем с чистой базы, UI восстановления нового аккаунта остаётся.

5. Проверки и визуальная приёмка

После каждого крупного блока сравни реальные web и Android скриншоты одинакового состояния/размера, просмотри их сам и исправь расхождения. Подготовь пары «эталон / раньше / после» и контактный лист либо локальный HTML-отчёт с понятными подписями; не подменяй Android screenshot макетом. Основной агент должен иметь возможность открыть все пары и проверить их независимо.

В матрице отдельно оцени: расположение/размер поля и панелей, цвета/шрифты/графику, путь выбора символа/клетки/направления, отсутствие лишних шагов, скролл/масштаб и конечные состояния. Перечисли неизбежные платформенные отличия конкретно, без общего заявления «нативная адаптация». Крупное отличие или непройденный сценарий означает открытый пункт, а не PASS. При принципиальной неоднозначности сначала сверь исходник/живой эталон, затем сообщи основному агенту; не придумывай новый дизайн самостоятельно.

Адаптируй существующие UI-тесты к восстановленному пользовательскому сценарию. Не оставляй тест, который обходит основной UI через формы координат или прямые repository-команды и объявляет управление принятым. Проверь реальными касаниями: расстановку, направленный и ненаправленный ход, отмену, телепорт, конец партии, оба размера поля; отсутствие лишней команды после pan/zoom и двойного нажатия. Проверь актуальные обычный/локальный/командный сценарии в пределах затронутого отображения и чей ход показан.

Выполни релевантные Kotlin unit tests, lint и R8 QA build. UI-прогон как минимум на доступных Android26 и36 эмуляторах, включая узкий viewport, поворот/Activity recreation там где разрешено, увеличенный системный шрифт, потерю/возврат сети, фон и force-stop. Не ослабляй TLS/cleartext/security config. Локальный devQa может использовать предусмотренный loopback endpoint; не выдавай тест локального варианта за повторную production HTTPS-проверку.

Синтетические fixtures и screenshots без секретов. Не удаляй пользовательский package/данные на физическом устройстве. Закрывай только созданные процессы, временные контейнеры/сети и собственные эмуляторы по точным именам. Не выполняй широкую очистку Docker или рабочего дерева. Новый UI не должен ломать существующие токены/аккаунты при обновлении установленного APK.

6. Передача результата

Собери новый prodQa APK с -PSYMBOLS_PROD_URL=https://symbols-api.votarumshee.com, той же QA-подписью и package com.votarumshee.symbols.qa, чтобы пользователь мог обновить выданную сборку. Не меняй production ключи/магазинные данные. Сохрани прежний APK; новому дай однозначное имя, например symbols-prod-qa-web-ui-20261007.apk в Client/artifacts/delivery. Сохрани SHA256, appId/версию, сертификат подписи, endpoint и список проверенных вариантов. Если UI проверялся в devQa с тем же кодом/R8, а prodQa только собран и статически проверен, скажи это явно. Не подключай exact prodQa к production ради создания синтетических пользователей.

Обнови Client/docs/web-ui-parity.md, feature-matrix.md, verification.md и отдельный манифест нового артефакта. Старую техническую приёмку API не переписывай как доказательство нового визуального соответствия. Сохрани повторяемые тестовые сценарии и результаты; артефакты/БД/секреты в Git не добавлять.

В финале передай основному агенту: что изменено по экранам/управлению; пути парных скриншотов и отчёта; результаты UI26/36, lint/unit/R8 и функциональных проверок; APK/SHA256; реальные остатки; подтверждение, что production не изменялся. Основной агент будет просматривать изображения и проверять поведение/код отдельно и может вернуть на исправления. Не объявляй визуальную задачу завершённой только по green build или наличию функций.
