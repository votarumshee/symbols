Реализация
1. Снять безопасный baseline production: image/config hashes, container IDs/start
   time, health, текущие mounts/networks, схема БД (без игровых данных/секретов).
   Оценить RAM/disk/CPU. Сохранить конфигурацию и план отката до изменений.
2. Отдельный Compose project symbols-staging; отдельные PostgreSQL container и
   volume, API, internal DB network, frontend network, аватары, env и каталоги
   releases/current. Имена, подсети, статические IP и локальные порты не должны
   пересекаться с production. БД без опубликованного порта, API не доступен извне
   в обход HTTPS proxy. Контейнер API не должен иметь прямого доступа к production
   DB/network/volume/secrets. Удаление staging не должно затрагивать production.
3. Сгенерировать отдельные DB owner/runtime/admin passwords и metrics token;
   root-only файлы/права 0600. Никаких production env в staging контейнерах.
   PostgreSQL owner/runtime имеют такие же минимальные права, как в production.
   Только новая чистая база + migrations/seed/grants; не копировать игроков.
4. Развернуть серверный образ опубликованного main. Собрать web из ТОГО ЖЕ commit
   с native API https://symbols-api-staging.votarumshee.com; фиксировать SHA и
   contentVersion/assetVersion. WEB_ORIGIN равен staging web HTTPS origin.
   Не обходить production APK guards: staging APK сейчас не входит в задачу.
5. Общий Caddy обслуживает оба новых имени с отдельными TLS сертификатами и
   отправляет трафик только в staging API/static. Browser API остаётся same-origin.
   Не занимать 80/443 вторым Caddy. Предпочесть reload. Если нужна новая сеть Caddy,
   подключение должно быть декларативным и переживать recreation/reboot;
   не оставлять docker network connect единственным источником конфигурации.
   Валидировать весь Caddyfile перед применением. Production routing сохранить.
6. Ограничить RAM/CPU/pids/log size staging с учётом VDS 4GB; оставить резерв
   production. Настроить healthchecks и restart unless-stopped. Метрики закрыты.
   Staging страницы не индексируются (X-Robots-Tag noindex, nofollow).
7. Отдельный ежедневный локальный backup staging в собственный каталог/lock,
   retention 3-7 копий. Проверить restore в disposable staging DB. Не менять
   production restic repository, backup locks, timers и retention. Не подключать
   offsite staging автоматически: описать, что локальный staging backup находится
   на том же VDS, а offsite production остаётся действующим.
8. Сохранить воспроизводимую конфигурацию/скрипты в Server/deploy/staging/ и
   инструкции эксплуатации в Server/docs/staging.txt. Примеры env без секретов.
   Если требуется изменить общие production-файлы, сообщить root до изменения.
   Зафиксировать команды запуска/обновления/отката/удаления только staging,
   безопасные image IDs, source SHA, пути, версии, лимиты и результаты проверок.

Приёмка (предоставить фактические доказательства, не только описание)
