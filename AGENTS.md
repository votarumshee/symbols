# Правила работы с репозиторием «Символы»

Эти правила распространяются на весь репозиторий. Перед изменениями прочитай
этот файл, проверь текущую ветку, `git status` и инструкции нужного компонента.
Прямые указания пользователя имеют приоритет. Не теряй чужие или незакоммиченные
изменения; при параллельной работе явно разделяй области ответственности.

## Ветки и поток изменений

Основной поток: `ветка задачи → staging → PR → main`.

- `main` — проверенная версия для production. Не вести разработку на `main`,
  не создавать в ней коммиты напрямую и не выполнять прямой push в `main`.
  Изменения попадают в `main` только через PR с исходной веткой `staging`.
- `staging` — общая интеграционная ветка для разработки и тестирования перед
  релизом. Отдельная ветка `develop`/`developer` пока не используется.
- Для КАЖДОЙ фичи, бага и задачи, включая документацию и инфраструктуру,
  создавать отдельную ветку от актуальной `staging`. Примеры:
  `codex/feature-<name>`, `codex/fix-<name>`, `codex/task-<name>`.
- Реализация, тесты и коммиты задачи выполняются только в её ветке.
  Не смешивать независимые задачи в одной ветке или коммите.
- Завершённую ветку после проверки изменений и успешных применимых тестов
  вливать в `staging`, предпочтительно через PR `ветка задачи → staging`.
  Если выполняется локальный merge, сначала проверить diff, затем сделать merge
  и push только в `staging`. Прямые коммиты реализации в `staging` не делать.
- Релиз оформлять отдельным PR `staging → main`. Перед слиянием проверить
  актуальный SHA, отсутствие конфликтов, результаты CI и приёмку на staging.
  Не считать проверки предыдущего SHA проверками новых изменений.
- Слияние PR в `main` и production-развёртывание выполнять только в рамках
  поручения пользователя. Разрешение создать PR само по себе не означает
  разрешения объединить его или выпустить приложение.
- Для долгоживущих веток предпочитать merge с сохранением истории. После
  релиза синхронизировать `staging` с `origin/main` через merge при необходимости.
  Не переписывать опубликованную историю `main`/`staging`, не использовать
  force-push и не обходить защиту веток.
- При начале задачи выполнить fetch, проверить существование веток и их
  расхождения. Не сбрасывать локальные изменения ради переключения ветки.

## Устройство проекта

- `WebClient/src/` — поддерживаемый общий web-клиент. Браузер и Capacitor
  используют один исходный UI; мобильный клиент загружает упакованные ресурсы.
- `WebClient/android/` и `WebClient/ios/` — native-оболочки и интеграции.
- `Server/` — API v3 и PostgreSQL. Сервер определяет результаты ходов,
  баланс, награды и состояние аккаунтов; клиент не подменяет эту логику.
- `Client/` — сохранённый Kotlin-клиент и проверка миграции его аккаунтов.
- Корневой исторический web/SQLite-проект, `dist/`, `legacy/` и экспортированные
  данные нужны для эталона и совместимости. Не принимать их за текущий production.
  Сохранять LICENSE, NOTICE и происхождение сторонних ресурсов.

## Разработка и проверки

- Вносить минимальные изменения для задачи. При исправлении ошибки добавлять
  регрессионную проверку поведения, включая затронутые гонки и восстановление.
  Для одной правки документации достаточно проверить содержание и diff.
- Использовать Node.js 24, lock-файлы и существующие команды проекта. Перед
  изменением API сверяться с `contracts/` и клиентами; не ломать native Bearer,
  browser cookie, идемпотентность команд и восстановление соединения.
- Для серверных изменений: `npm --prefix Server run build`,
  `npm --prefix Server test` и из каталога `Server/`
  `node scripts/contracts.mjs --check`.
- Для web-изменений: `npm --prefix WebClient test`,
  `npm --prefix WebClient run build` и подходящие сценарии
  `npm --prefix WebClient run test:e2e`.
- Тесты с БД должны использовать настроенный `TEST_DATABASE_URL` для отдельной
  локальной PostgreSQL. E2E — только disposable БД на loopback. Не запускать
  интеграционные тесты, seed тестовых ресурсов или нагрузку на production.
- Для native-изменений выполнить относящиеся к ним build/проверки платформы.
  Успешная сборка iOS не заменяет испытание на устройстве, а Kotlin-тесты не
  заменяют проверку Capacitor. Указывать фактические ограничения приёмки.
- Для production web/APK задавать
  `SYMBOLS_NATIVE_API=https://symbols-api.votarumshee.com`; после сборки запускать
  `check:release` в `WebClient` с `SYMBOLS_RELEASE_CHECK=production`.
- Для тестового Android APK использовать существующий QA-ключ, тот же package
  для обновления и увеличенный `versionCode` при выпуске новой версии.
  Не удалять установленное приложение с данными ради установки обновления.
  QA-подпись не выдавать за подпись для публикации в магазине.
- Перед коммитом проверить `git diff`, staged-файлы и `git diff --check`.
  Перед передачей результата указать выполненные проверки и то, что не проверено.

## Окружения и развёртывание

| Окружение | Сайт | API для native-клиента |
|---|---|---|
| Production | `https://symbols.votarumshee.com` | `https://symbols-api.votarumshee.com` |
| Staging | `https://symbols-staging.votarumshee.com` | `https://symbols-api-staging.votarumshee.com` |

- Оба окружения находятся на одном VDS, но используют отдельные API, PostgreSQL,
  Docker-сети и тома, аватары, секреты и резервные копии. Не копировать production
  env в staging, не подключать staging к production БД и не переносить игроков
  в тестовое окружение без отдельного поручения.
- Браузер обращается к `/api/web/v3/*` через собственный origin. `WEB_ORIGIN`
  должен точно соответствовать сайту окружения. Сохранять проверку Origin,
  Secure/HttpOnly/SameSite cookie и отсутствие bearer-токенов в browser JavaScript.
- Общий Caddy направляет запросы по доменам. Staging API service называется
  `api`, его уникальный alias — `symbols-staging-api`; не называть его `server`,
  поскольку это имя production upstream. Проверять DNS внутри Caddy.
- До инфраструктурных изменений сохранить конфигурацию и план отката.
  Перед изменением Caddy проверять полный конфиг. При обновлении production
  runtime сохранять подключение staging-сети согласно
  `Server/docs/staging.txt` и `Server/deploy/staging/patch-ingress.py`.
- Staging должен сохранять ограничения ресурсов и отсутствие публичных портов
  API/БД. Не пересоздавать production API/БД в ходе staging-операций.
- Развёртывать воспроизводимые артефакты конкретного commit SHA, фиксировать
  image ID, версии web-ресурсов и результаты smoke-проверок. Ветка Git сама
  по себе не переключает окружение: push/merge не считать фактом деплоя.
- Перед production-миграцией проверить свежую резервную копию и восстановление.
  Не редактировать уже применённые миграции; добавлять новые. Не восстанавливать
  старую БД поверх новых игровых данных как обычный способ отката приложения.
- Staging backup сейчас ежедневный локальный, хранит семь копий на том же VDS.
  Production использует Google Drive/restic. Не менять production retention,
  backup locks, таймеры и репозиторий копий при работе со staging.
- Порядок выпуска, проверки и отката: `Server/docs/deployment.md`,
  `Server/docs/staging.txt`, `WebClient/docs/deployment.md`.
  Исторические отчёты описывают состояние на дату проверки; перед операциями
  проверять фактическую конфигурацию сервера.

## Секреты, артефакты и PR

- Не коммитить пароли, реальные env-файлы, SSH/OAuth/подписывающие ключи, токены,
  дампы игроков, APK, keystore и временные отчёты. Примеры env — с placeholders.
- Не печатать секреты в логах, сообщениях или PR. Полный вывод Docker Compose
  config и inspect env может содержать пароли; использовать безопасные выборки.
- APK и подробные тестовые отчёты хранить в игнорируемых каталогах артефактов;
  в Git сохранять исходники, конфигурацию, тесты и безопасную документацию.
- В PR описывать проблему, итоговое поведение, проверки и ограничения. Для
  миграций и инфраструктуры указать влияние на данные и процедуру отката.
- Эти инструкции задают процесс работы; настройки branch protection и CI/CD
  на GitHub настраиваются отдельно. Не заявлять, что они включены, без проверки.
