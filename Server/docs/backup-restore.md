# Production backup and restore

This VDS uses root-owned local dump scripts; the older `deploy/backup.sh` and `symbols-backup.*` are a separate SSH-pull design for a different backup host and are not installed here.

## Installed operation

`install-backup.sh` installs fixed-purpose scripts in `/usr/local/sbin`, generates systemd units, and initially enables only `symbols-backup-local.timer` (hourly UTC) and `symbols-monitor.timer` (every5 minutes). On2026-10-07 all four external timers were enabled after authorized OAuth, successful uploads and an isolated external restore. Upload is scheduled hourly at minute10, check daily04:25UTC, prune Sundays04:40UTC, full read first day monthly05:20UTC. Timers are persistent; jobs share flock and have bounded execution times. Unit templates are reproducibly generated by the installer. See [external acceptance evidence](vds-external-backup-verification.md).

Local dumps: `/var/backups/symbols/hourly/YYYYMMDDTHHMMSSZ`, mode0700, `pg_dump -Fc` inside the PostgreSQL17 container. Temporary directory, list validation, checksums and atomic publication preserve the last successful copy on failure. Local-only mode explicitly retains24 successful copies; insufficient free space fails before dump. Once external mode is enabled, older local copies are deleted only if uploaded, and the free-space guard stops growth during prolonged upload failures.

Each bundle contains dump, avatars.tar, restricted configuration.tar, roles.sql and metadata. The configuration/roles archives contain secrets: never publish them. Metadata contains commit/image/version/time; database counts are a **post-dump observation**, not the same MVCC snapshot and not a transactional reconciliation proof. Compare invariants on a restored database. SQL and avatars are not atomic: current avatar set is empty; before introducing mutable uploaded files adopt a maintenance/quiescence or versioned-object procedure for a consistent DB/files point.

## Google Drive activation and credential recovery

1. Owner selects/authorizes the Google account and a dedicated backup directory. Do not copy tokens from another app/connector or paste them into chat.
2. Use interactive SSH and `sudo rclone config --config /etc/symbols/rclone.conf`, create remote `symbols-drive` of type `drive`. Follow [rclone headless OAuth procedure](https://rclone.org/remote_setup/) in the owner's browser. For a dedicated root_folder_id set it privately; limit remote scope/access appropriately. Config file0600, directory0700.
3. Preserve `/etc/symbols/restic-password` outside the VDS through a secure interactive channel. With the owner's explicit permission, its recovery copy was saved on 2026-10-07 at `Server/private/recovery/restic-password.txt` on the owner's Windows machine. This directory is ignored by Git and its Windows ACL allows only the owner and SYSTEM. OAuth tokens were not exported. Keep an additional copy in the owner's password manager; losing both the VDS and this computer would otherwise lose the decryption password. Recover Google access by authorizing rclone again in the same Google account; restore private application configuration from the encrypted backup.
4. Review `/etc/symbols/backup.env`; its default is `rclone:symbols-drive:symbols-production-restic`. Export those three variables in a root shell, use `rclone lsd symbols-drive:` to verify the selected location, then `restic init` **only for a new empty repository**. Never reinitialize an existing repository.
5. Create root-only `/etc/symbols/external-backup.enabled`, run `systemctl start symbols-backup-upload.service`. Check an actual remote snapshot, download that exact snapshot, verify checksums and restore into an isolated database as below. Until this succeeds external protection is incomplete.
6. After acceptance enable `symbols-backup-upload.timer`, `symbols-backup-check.timer`, `symbols-backup-prune.timer`, `symbols-backup-full-check.timer`. Check logs and snapshot freshness. Do not enable public Caddy proxy before acceptance.

Restic encrypts before rclone uploads. No `rclone sync` of the live DB. Restic uses stable source path/host/tag and source-dump time; retention24hourly/14daily/4weekly. A failed upload never marks that dump uploaded and cannot update freshness. Empty upload passes do not refresh data age. Pruning is separate and requires a recent successful external data timestamp. [Restic rclone backend](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html#other-services-via-rclone), [rclone Drive](https://rclone.org/drive/).

The authorized rclone remote uses `drive.file`, scoped to files created/opened by that OAuth application. The dedicated folder is [symbols-production-restic](https://drive.google.com/drive/folders/1Q7POLQHf2GKa8WgXskJprLHZXlTb_n7B). Its contents are encrypted restic objects, not directly readable SQL files. The initial upload encountered transient Google per-project request limits for rclone's shared OAuth client and recovered through retries. Repeated delays or stale snapshots warrant a dedicated OAuth client; switching clients with `drive.file` requires checking access to the existing repository before retiring the old configuration. This request quota is separate from Drive storage capacity. Private restic cache is `/var/cache/symbols/restic`, mode0700.

## Restore

Lock `/run/lock/symbols-backup.lock` for external retrieval/check/restore so maintenance cannot intersect it. Disable relevant timers during a long recovery if necessary. In a protected working directory:

```sh
set -a
. /etc/symbols/backup.env
set +a
restic snapshots --tag symbols-hourly
restic restore EXACT_SNAPSHOT_ID --target /var/backups/symbols/restore-private
```

Use a concrete snapshot ID; locate its `upload-current` bundle, validate checksums, restore required protected config/role definitions privately. Create a **new** PostgreSQL17 test database owned by symbols_owner, then:

```sh
pg_restore --no-owner --no-privileges --exit-on-error --single-transaction --dbname "$RESTORE_DATABASE_URL" symbols.dump
```

Supply credentials via a protected environment/.pgpass, never command logs. Run the exact application image's grants script as owner, then the app as symbols_app. Verify migrations/content/counts, balances/inventory and domain invariants, authentication, API/WS and avatar consistency. Production remains pointed at its existing DB until recovery is deliberately accepted. `verify-runtime.sh` demonstrates isolated local restore and synthetic-account equality; it does not download a remote snapshot.

`verify-external-backup.sh` checks the remote repository, selects a concrete snapshot, downloads and verifies all restored files, validates bundle SHA256 checksums, and restores the dump in an isolated PostgreSQL container/internal network. It uses the application image recorded in that snapshot and checks restricted-role readiness, registration, bootstrap, trial start and idempotent replay. It writes non-secret evidence to `/var/lib/symbols/backup-state/external-restore.json` and removes its temporary resources. This is an on-demand acceptance drill; the scheduled full check verifies stored data integrity without running the application restore drill.

For total VDS loss: new Ubuntu→host scripts→Docker/firewall→privately restore config/role credentials→retrieve the exact application image from retained local archive/registry→retrieve and restore the selected backup→grants/avatars→isolated readiness/game/WS checks→TLS and DNS switch. Application archive must also be available outside the lost host (currently `Server/private/releases/symbols-c76fcae8e802.tar` on the owner's Windows machine, ignored by Git; registry release automation and durable archival policy are pending). Recovery timing includes these dependencies; a13-second tiny local drill is not evidence of a two-hour full-host disaster recovery SLA.

When real users exist, maintain an external deletion ledger and reapply deletions since the backup before reopening service, so a restore does not resurrect deleted accounts.

## Monitoring

Timestamp files under `/var/lib/symbols/backup-state` distinguish local backup completion, externally stored source-data age, and external operation time. Missing/older-than2h local/external data, disk≥85%, failed `/ready`, container unhealthy/restart counts and scheduler lag≥30s produce local journal/service failure signals.

No external notifications are active. Owner may install root-owned `/etc/symbols/notify` to integrate the chosen channel; do not embed tokens in repository units/scripts. An external observer is required to detect complete VDS loss, which a local timer cannot detect.
