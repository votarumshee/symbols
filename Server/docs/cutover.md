# Private data import and production cutover

The public export contains no working accounts. No live players have been imported by this change. Required private sources: a consistent full D1 SQLite database (or D1 SQL dump) containing profiles, matches, recovery, recovery_limits, vaults, listings, arenas, operations and account_sessions; optionally an R2 export of `avatars/...jpg` with a JSON manifest of `key` and `sha256`. Obtain them through the owner's private transfer channel. Never paste dumps/tokens in chat, Git URLs or PRs.

## Dry run

Use an isolated staging database already migrated and seeded. Store inputs in ignored `Server/private/`, restrict OS permissions and delete according to the agreed retention. `npm run db:import -- private/export.sqlite --report=private/dry-run.json` validates and executes the entire import in a transaction that is rolled back. For SQL dumps pass a `.sql` file; it executes only in a temporary in-memory SQLite database before conversion. The application never interprets SQL from HTTP.

Review the private report: source counts, exact integer sum of balances, per-symbol ownership sums, skin/avatar ownership equality, open listing count and rejected IDs/errors. No malformed row is silently skipped; any validation/reconciliation/database error prevents the whole import. Invalid foreign keys, collisions with existing IDs and price/price_cents disagreements block import. If balanceCents exists it is the authoritative stored wallet; old balance is its display cache. If absent, the decimal representation is parsed with BigInt, never multiplied/rounded as float. IDs remain text; timestamps map UTC milliseconds to timestamptz. Unknown oversized integers fail validation rather than losing precision.

Apply with `--apply` only after review. The file SHA-256 is recorded in `imports`; an identical second import is a no-op. Different dumps with colliding IDs fail; this is not a merge/update tool. A production final import should target a clean migrated database, not the previous dry-run clone.

Mapping: profiles retain identity and private legacy JSON; vaults preserve authoritative v2 progress, balances, inventory, upgrades, XP/rank, history and cosmetics. If a profile has no vault, only server-stored old progress is converted; HTTP never accepts localStorage. listings preserve IDs, integer cents and escrow ownership; sessions retain compatible SHA-256 hashes with a 30-day transition expiry; recovery retains existing SHA-256 code hashes. recovery_limits are copied. All nine tables additionally enter private `legacy_rows` for audit, including historical matches and D1 operation receipts. Those receipts do not authorize v3 retries. Old live sessions can authenticate during the transition; recovery on Android revokes all previous sessions and issues a new bearer token. A lost code/token cannot be reconstructed from a hash. Browser-only progress has no automatic trusted import: require owner-reviewed evidence matched to a verified existing identity, otherwise it cannot be credited safely.

Unfinished matches are archived and cancelled without new wins, XP or currency; all imported vault game pointers are cleared. Already consumed match inventory remains as persisted. Explain this pause policy to players before cutover. Open market listings remain open and reserved; do not re-add their items to inventory. Closed listing ownership and legacy history are retained. The original website already disallows arbitrary avatar uploads; new uploads remain disabled. For a validated R2 export use `node scripts/import-avatars.mjs private/avatar-manifest.json private/r2 private/avatars` then repeat with `--apply`. It checks path, owner, JPEG size/signature and hash, and refuses different-content overwrite. Compose mounts that directory with deletion-worker write access at `/avatars`.

## Owner-approved switching sequence

1. Back up current D1/R2 and record the old deployment version. Validate that backup separately.
2. Run staging import and reconciliation; test old nine-digit recovery and both game sizes/modes on the future client. Confirm content/API commit with Client.
3. Schedule a maintenance window and explain unfinished-match policy. Only with the owner's approval stop all old writes (including queues/ticks and legacy endpoints). Do not change the live site during development.
4. Export a final consistent D1 database and R2 manifest after the write freeze. Record checksums, counts, balance sums and escrow quantities. Keep the old service read-only/offline.
5. Import into the final empty migrated PostgreSQL database; reconcile the report, recover representative authorized accounts, inspect inventory/cosmetics/history, run a synthetic match and backup/restore smoke test.
6. Switch the v3 clients to the verified HTTPS endpoint, monitor commands/events, and retain the old system frozen. There must never be independent writes to both databases.
7. Before any rollback freeze new writes too. If PostgreSQL has accepted no player writes, restore old routing from the verified frozen snapshot. If new writes exist, first capture PostgreSQL backup plus all post-cutover commands/events and reconcile their effects under owner review; blindly returning to old D1 loses money/items/progress. Prefer repairing forward. No automatic reverse merge is claimed.

Imported avatar access checks that the owning account still exists. Deletion revokes HTTP access immediately and enqueues physical removal in `avatar_deletions`; the persistent maintenance worker removes files on its next pass. Give the container's UID 1000 write permission only to the imported avatar directory. Other assets stay read-only. For local execution set AVATAR_ROOT to that same directory. Do not put a CDN cache in front of `/avatars`.

Record the cutover timestamp, import digest, binary/contract commit, reconciliation approval and rollback decision privately. Real cutover and production site/configuration changes require a separate explicit owner approval of the tested result.
