Isolation and limits
--------------------
Compose project: symbols-staging. Services: db, api, optional tools-profile migrate.
Important: staging API service MUST NOT be named server. Docker supplies an implicit
service-name alias. The shared proxy resolves production upstream server:3000;
another server alias on a connected network would make routing ambiguous.
Staging upstream has the explicit unique alias symbols-staging-api:3000.

symbols_staging_database: internal bridge 172.30.52.0/24, only staging db/api/tools.
symbols_staging_frontend: bridge 172.30.51.0/24, API .2 and shared Caddy .3.
No staging API or DB published ports. Staging API has no production DB network,
volume, bind mounts or env file. Only Caddy bridges both frontend networks.
PostgreSQL volume: symbols_staging_pgdata. Clean migrations 0001-0004 + content seed.
DB roles symbols_owner and symbols_app are separate roles on the separate cluster.
Runtime has no superuser, createdb, createrole, schema-create or migration-table access.
Secrets: /etc/symbols-staging/staging.env, root:root 0600, independently generated.
Avatars: /var/lib/symbols-staging/avatars, uid/gid1000, directory0750.
API:384MiB, 0.5CPU, 128pids, pool4. DB:512MiB, 0.5CPU, 128pids, shm128MiB.
Migration:256MiB, 0.5CPU, 64pids. Docker local logs5MiB x2 each.
Healthchecks enabled, runtime restart unless-stopped. Metrics blocked by Caddy.

Shared Caddy configuration
--------------------------
There is ONE Caddy, no second listener on80/443. Its production compose file
declares external symbols_staging_frontend network with Caddy172.30.51.3.
This declaration is added idempotently by patch-ingress.py; it is not merely a
docker network connect operation. Static staging files use the existing RO
/srv/symbols-web mount. Production web current symlink was not changed.

CRITICAL FOR FUTURE PRODUCTION DEPLOYMENTS:
Before selecting a new production runtime or recreating Caddy, apply:
  python3 /opt/symbols-staging/current/patch-ingress.py NEW_RUNTIME/compose.production.yaml
  docker compose --env-file /etc/symbols/production.env -f NEW_RUNTIME/compose.production.yaml --profile public config --quiet
The staging frontend network must already exist. Keep staging.caddy in the imported
directory. Losing this declaration breaks staging ingress after Caddy recreation.
Production API and DB do not need a restart for staging changes.

Initial installation (root, using reviewed files)
-------------------------------------------------
1. Export exact released gitSHA into an isolated build directory, including
   WebClient/src, scripts/build.mjs, package*.json, Server/content/catalog.json.
2. In exported WebClient run npm ci --ignore-scripts and build with environment
   SYMBOLS_NATIVE_API=https://symbols-api-staging.votarumshee.com.
   Package the resulting www with Server/deploy/staging/ files.
3. Verify image ID and sourceSHA in install.sh. Run bash install.sh as root.
   It generates fresh secrets only when staging.env does not exist, starts clean DB,
   applies migrations/seed/grants, starts API, installs backup service and web assets.
4. Once both A records resolve to135.106.172.96, run bash activate-ingress.sh.
   It checks alias collision, checkpoints production compose/container identity,
   validates Caddy/compose, recreates ONLY Caddy, checks production ready and identity.
   A failed activation restores previous compose and removes staging hostfile.
5. Validate real trusted HTTPS for both hosts (never use curl -k), auth isolation,
   and browser UI before announcing readiness.

Update staging
--------------
1. Select a tested source SHA and build immutable server image and web from it.
   Do not copy a production env file. Keep the unique api service and aliases.
2. Run symbols-staging-backup; record previous runtime, image and web symlink.
3. Copy reviewed staging config into a new /opt/symbols-staging/releases/<SHA>.
   Set staging.env SYMBOLS_IMAGE/GIT_COMMIT to reviewed image/SHA without displaying it.
4. Switch /opt/symbols-staging/current, run symbols-staging-compose config --quiet,
   symbols-staging-compose run --rm migrate, symbols-staging-compose up -d --wait api.
5. Place verified web assets under a new assetVersion path and atomically select
   staging/current. Reload Caddy only if routes changed. Verify contentVersion match.
6. Run HTTPS/auth/isolation acceptance. Do not update production in this procedure.

Rollback
--------
App-only: restore previous staging image/config/web selections, recreate staging api.
For incompatible migrations restore a staging backup into a replacement staging
database; never point staging at production DB and never restore over production.
Initial ingress checkpoint:
  /var/lib/symbols-staging/checkpoints/20261009T121741Z/compose.production.yaml
To undo only staging ingress: remove /srv/symbols-web/caddy/staging.caddy, use
patch-ingress.py /opt/symbols/current/compose.production.yaml --remove, validate
compose and full Caddy config, then symbols-compose --profile public up -d
--no-deps --force-recreate caddy. This detaches Caddy from staging persistently.

Backups and restore
-------------------
Timer symbols-staging-backup.timer: daily04:35UTC +random0-10min, Persistent=true.
Separate lock /run/lock/symbols-staging-backup.lock; retains latest7 successful copies.
Manual: symbols-staging-backup. Backups include custom-format DB dump, avatars and
staging config/env; root-only directories/files. Avatar copy is not transactionally
atomic with database. Immutable web assets can be rebuilt from sourceSHA.
Verify: bash /opt/symbols-staging/current/verify-restore.sh.
The verifier creates an internal-network disposable PostgreSQL, restores without
owner/ACL, checks profile count and migration/content metadata, then removes its
container, anonymous volume and network. This does not replace live staging DB.
Actual disaster recovery must recreate roles from staging.env/init-roles.sh and
apply grants (the verifier's --no-acl restore is not a production-role restore).
Staging backups are ON THIS VDS ONLY, not offsite. Production Google Drive/restic,
backup locks, timers and retention remain unchanged.

Remove staging (production remains)
-----------------------------------
First remove ingress as above, ensuring Caddy no longer uses staging network.
Then systemctl disable --now symbols-staging-backup.timer and
symbols-staging-compose down. This stops only project symbols-staging and keeps DB.
Do NOT add -v unless explicitly deciding to erase all staging data. Before any
deletion, inspect exact paths and volume name symbols_staging_pgdata.
Do not remove /srv/symbols-web parent, production volumes or shared Caddy volumes.
Backup/config/avatar deletion is a separate explicit data-retention decision.
